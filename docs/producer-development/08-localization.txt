VYAPARSETU — PRODUCER LOCALIZATION FOUNDATION
============================================================

1. LOCALIZATION ARCHITECTURE
============================================================
The application utilizes Flutter's official internationalization system:
- Configuration via l10n.yaml.
- Translation source files in ARB format:
  * lib/core/localization/l10n/app_en.arb (English - Template & Fallback)
  * lib/core/localization/l10n/app_hi.arb (Hindi - Devanagari script)
  * lib/core/localization/l10n/app_pa.arb (Punjabi - Gurmukhi script)
- Code generator compiles type-safe localizations into:
  * lib/core/localization/generated/app_localizations.dart
  * lib/core/localization/generated/app_localizations_en.dart
  * lib/core/localization/generated/app_localizations_hi.dart
  * lib/core/localization/generated/app_localizations_pa.dart
- MaterialApp integration in lib/main.dart provides AppLocalizations.supportedLocales
  and AppLocalizations.localizationsDelegates.
- English ('en') is configured as the default and fallback locale.

2. SUPPORTED PROTOTYPE LANGUAGES & EXPANDABILITY
============================================================
Currently supported prototype languages:
1. English (en)
2. Hindi (hi) — हिन्दी
3. Punjabi (pa) — ਪੰਜਾਬੀ

The architecture is designed to expand to additional scheduled Indian languages
(e.g., Bengali, Marathi, Telugu, Tamil, Gujarati, Kannada, Odia, Malayalam, Assamese)
by adding standard app_<lang>.arb files to lib/core/localization/l10n/ and updating
the AppLanguage enum.

4. APP LANGUAGE VS VOICE GUIDANCE LANGUAGE SEPARATION
============================================================
Two distinct concepts are maintained in LanguageProvider:
- App Language (AppLanguage):
  * Controls all visible text in the application interface.
  * Updates MaterialApp locale and triggers immediate UI rebuilds.
- Voice Guidance Language (VoiceLanguage):
  * Will control future audio playback, speech prompts, and text-to-speech (TTS).
  * Maintained as an independent setting so a user can visually navigate in one language
    while hearing voice guidance in another (or keep preferred regional dialects).
  * TTS and voice services are intentionally deferred and not implemented in Step 5A.

5. NEW SCREENS & ONBOARDING MIGRATION POLICY
============================================================
- New Producer screens (e.g. Dashboard, Product Catalog, Market Radar) MUST use
  AppLocalizations.of(context)! rather than hard-coding user-facing strings.
- Existing onboarding screens (Steps 1–4) are NOT required to be migrated in this
  milestone, preventing regressions to existing tested onboarding flows.
- Language switcher widget (LanguageSwitcherWidget) is modular and reusable across
  app bars, menus, and future settings screens.

6. CORE UX LANGUAGE & LOW-LITERACY NAMING PRINCIPLE
============================================================
- Principle: A page or action name must clearly tell the producer what they will find
  or what will happen after tapping it.
- UI labels prioritize clarity and immediate understanding over branding or startup jargon.
- Avoid fancy, technical, startup-style, analytics-style, or English-heavy terminology.
- Technical module names can differ from visible page names. Internal architecture, code,
  and SIH documentation may retain technical module names while UI labels remain simple.
- Simple native-language wording in natural phrasing is preferred; avoid literal translations
  of technical English terms.

Guideline mapping examples:
- Internal: AI Product Studio
  User-facing: Add Product / Improve Product Photo
- Internal: Market Radar
  User-facing: What Buyers Want
- Internal: Pricing Assistant
  User-facing: Set a Good Price
- Internal: Catalogue
  User-facing: My Products
- Internal: Buyer Request Matching
  User-facing: Buyer Needs / Matching Buyers
