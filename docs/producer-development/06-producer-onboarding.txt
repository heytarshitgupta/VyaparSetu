5. RUNTIME ISSUE RESOLUTION: UPDATED_AT COLUMN PRIVILEGE (42501)
------------------------------------------------------------
- Symptom: Real manual testing of Step 1 save failed with "Failed to save basic details".
- Root Cause: Flutter client payload manually included 'updated_at': DateTime.now().toIso8601String(). In Migration 001, 'updated_at' was intentionally excluded from client UPDATE privileges (GRANT UPDATE only covers user-editable columns). PostgreSQL returned code 42501 (permission denied for column updated_at).
- Fix Applied: Removed manual 'updated_at' from updateBasicProfile, updateBusinessProfile, and updateLocationProfile.
- Database Authority: Database triggers trg_profiles_updated_at and trg_producer_profiles_updated_at execute handle_updated_at() to manage timestamps automatically with SECURITY DEFINER. No SQL schema migration was required.

7. STEP 4E2.1 — RESUMABLE PRODUCER ONBOARDING
------------------------------------------------------------
A. Architectural Motivation:
- Micro-producers and artisans frequently navigate mobile browsers, experience connection drops, reload the application, or sign in across different devices.
- Without server-authoritative progress tracking, reloading the app always forced the user back to Step 1 (Basic Details), creating severe friction.
- Local-only solutions (SharedPreferences, localStorage) are strictly rejected because they do not survive cross-device usage or browser storage clearing and do not provide server-side trust.

B. Authoritative Server State:
- Column: public.producer_profiles.onboarding_step SMALLINT NOT NULL DEFAULT 1.
- Constraint: chk_producer_onboarding_step CHECK (onboarding_step >= 1 AND onboarding_step <= 5).
- Step Mapping:
  * 1 = Basic Details (Step 1)
  * 2 = Business / Craft Details (Step 2)
  * 3 = Location Details (Step 3)
  * 4 = Identity & Compliance (Step 4)
  * 5 = Review & Submit (Step 5)

C. Forward Progression & Trust Boundaries (Corrected Step 4E2.3):
- Direct client UPDATE on onboarding_step is completely excluded.
- Advancement occurs strictly through trusted SECURITY DEFINER RPC:
  public.advance_producer_onboarding_step(expected_current_step, next_step)
- Guarantees:
  * Caller identity derived solely from auth.uid().
  * Role check: Caller must be 'producer'.
  * Row Lock: Uses SELECT ... FOR UPDATE to serialize concurrent requests.
  * Expected Step Validation: Validates server_step = expected_current_step and next_step = expected_current_step + 1 (guards against stale state).
  * Server-Side Prerequisites: Validates saved database records (1->2 requires profiles.full_name; 2->3 requires producer_profiles business_name & craft_category; 3->4 requires valid location fields and pincode).
  * Step 4 -> 5 Blocked: Generic progression RPC rejects advancing past Step 4 ('identity_compliance_incomplete') because compliance completion rules are still evolving.
  * Monotonic & Idempotent: If server step >= next_step, the RPC succeeds as a no-op ('already_advanced') and will never regress progress.
  * Save-First Rule: Progress advances on the server ONLY after the corresponding step's form payload has been successfully persisted.
  * Status Protection: The RPC does NOT and cannot set onboarding_status = 'completed'. If status is already completed, returns 'already_completed' without mutation.

D. Backward Navigation:
- If a producer reaches Step 4 and presses "Back" to inspect Step 3 or Step 2:
  * In-memory UI step updates to allow reviewing or editing draft inputs.
  * Persisted server progress in public.producer_profiles remains at Step 4.
  * Re-saving Step 2 or Step 3 safely updates the respective form data without regressing onboarding_step.

E. App Start & Refresh Restoration:
- On screen load (ProducerOnboardingScreen._loadInitialData):
  * ProducerAuthService.fetchProducerProfile() retrieves the persisted producer_profiles row.
  * ProducerOnboardingProvider.initializeFromProfile() extracts onboarding_step (clamped 1 to 5) and restores _currentStep = onboarding_step - 1.
  * The user resumes directly at their furthest completed step with all previously saved draft fields fully populated.
- Completed Onboarding: If profiles.onboarding_status = 'completed', auth routing directs caller to /producer_home.

F. Existing Data Backfill Rule (Corrected Migration 007):
- For existing database records:
  * If onboarding_status = 'completed' -> Step 5
  * Else if Location details are complete (state, district >= 2 chars, city >= 2 chars, pincode ~ '^[1-9][0-9]{5}$', address >= 5 chars) -> Step 4
  * Else if Business details are complete (business_name >= 2 chars, craft_category non-empty) -> Step 3
  * Else if Profile full_name >= 2 characters -> Step 2
  * Else -> Step 1
- NOTE: PAN verification alone does NOT infer Step 5. Step 4 encompasses full identity and compliance.

G. PAN Verification Security & Preservation (Corrected Migration 006):
- Protection of Verified Identity: If caller has pan_verification_status = 'verified', a matching PAN returns 'already_verified' (idempotent success). A different or rejected PAN returns 'already_verified_conflict' and NEVER destroys, wipes, or regresses verified artifacts.
- Prototype Fingerprint: pg_catalog.sha256((v_pan || ':' || v_uid::TEXT)::BYTEA) is a prototype pseudonymous integrity fingerprint, not encryption or offline-secure protection. Production architecture will replace this with server-secret HMAC or tokenization vaults.
