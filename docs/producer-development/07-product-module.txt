DATABASE FOUNDATION ARCHITECTURE (STEP 6B.1)
------------------------------------------------------------
1. Canonical Schema:
   - Table: public.products
   - Primary Key: id UUID DEFAULT gen_random_uuid()
   - Ownership FK: producer_id UUID NOT NULL REFERENCES public.producer_profiles(id) ON DELETE CASCADE
   - Identity Relationship: producer_profiles.id == profiles.id == auth.users.id. Only verified/registered producers can own products.
   - Core Fields: name, description, category, price, unit, images, status, created_at, updated_at.

2. Product Lifecycle States:
   - Exactly 3 states: 'draft', 'active', 'hidden'.
   - 'draft': Work-in-progress, unlisted, visible only to owner.
   - 'active': Completed product, ready for future discovery, visible only to owner in Step 6B.
   - 'hidden': Temporarily delisted by producer (e.g. out of stock), visible only to owner.
   - No premature moderation workflows ('under_review', 'needs_changes', 'rejected') fabricated.

3. Pricing & Currency Rule:
   - Type: NUMERIC(12, 2) in INR (accommodates up to ₹9,999,999,999.99 with exact paise precision).
   - Drafts: Price may be NULL while incomplete.
   - Positive Price: If price is provided, it must be > 0.
   - Active Requirement: An 'active' product MUST have a valid positive price (> 0).

4. Text & Unicode Preservation:
   - Fields: name, description, category, unit.
   - Rule: Original user-entered Unicode text (English, Hindi, Punjabi, etc.) is preserved as-is.
   - Zero destructive overwriting with AI-generated or translated text.

5. Image Reference Strategy:
   - Field: images TEXT[] NOT NULL DEFAULT '{}'.
   - Storage-relative paths or references. Zero fake remote URLs.
   - Storage Bucket: Dedicated 'product-images' bucket and secure upload policies explicitly deferred to Step 6C.

6. Security & Row Level Security (RLS):
   - RLS strictly enabled on public.products.
   - SELECT, INSERT, UPDATE, DELETE strictly scoped to auth.uid() = producer_id.
   - Active products remain owner-only in Step 6B. Public/Buyer discovery deferred.
   - Hard Delete adopted for prototype simplicity.

7. AI & Voice Data Boundary:
   - Base table stores strictly canonical product attributes.
   - Zero speculative AI prompts, embeddings, audio blobs, or marketing metrics in the schema.
   - Future AI Studio and voice guidance will map directly to these canonical columns.

ADD PRODUCT DART DOMAIN, SERVICE & PROVIDER FOUNDATION (STEP 6C.4)
------------------------------------------------------------
1. ProducerProductDraft Domain Model:
   - File: lib/producer_section/products/models/producer_product_draft.dart
   - Purpose: Dedicated mutable/editable form draft state, strictly decoupled from canonical persisted ProducerProduct rows.
   - Defaults: name = '', category = '', description = '', pricePaise = null, unit = 'piece', images = const [].
   - Boundaries: Zero platform-specific types (no XFile, File, Uint8List, base64, or signed URLs). Only stable Storage object paths in images.

2. Centralized Exact Price Handling (ProductPriceParser):
   - File: lib/producer_section/products/models/product_price_parser.dart
   - Rule: Strictly integer paise (int? pricePaise). ZERO double parsing.
   - Parsing: Converts UI rupee text to paise (e.g. "1250" -> 125000, "1250.5" -> 125050, "0.01" -> 1).
   - Strict Rejections: Rejects zero ("0", "0.00"), negative values, >2 decimal places, alphabetic input, multiple decimal points, and values above Migration 009 NUMERIC(12, 2) maximum (₹9,999,999,999.99 = 999,999,999,999 paise).
   - Serialization: paiseToDecimalString converts paise to exact 2-decimal string for Supabase NUMERIC(12,2).

3. Create vs Update Draft Lifecycle:
   - createDraft: Requires authenticated user, forces producer_id = auth.uid(), forces status = draft, inserts allowed draft columns only.
   - updateDraft: Owner-scoped (id = productId AND producer_id = auth.uid()). Updates editable draft fields only. Does NOT modify producer_id, status, or images.
   - updateProductImages: Owner-scoped update specifically for stable Storage object paths.

4. Prerequisite: Product Must Exist Before Photo Upload:
   - Migration 011 Storage RLS strictly verifies:
     (1) First folder = auth.uid()::text
     (2) Second folder = owned product verified via private.producer_owns_product().
   - Therefore, a product record must be persisted in public.products BEFORE any photo can be uploaded to Storage.
   - In Step Navigation, advancing into Step 3 (Photos) automatically creates or syncs the draft record to ensure an authentic productId is available.

5. Image Storage Service Separation:
   - File: lib/producer_section/products/services/producer_product_image_service.dart
   - Contract: IProducerProductImageService
   - Bucket: Strictly private 'product-images' bucket (no caller-controlled bucket).
   - Filename Generation: Injectable SecureRandomFilenameGenerator creates 32-character collision-resistant hex names without user input or external packages.
   - Canonical MIME & Extension: Upload takes declared Content-Type, normalizes and validates it against allowlist (image/jpeg -> jpg, image/png -> png, image/webp -> webp), and internally derives the object extension. Caller cannot mismatch MIME and extension.
   - Validation Truthfulness: Declared MIME and 5 MB size checks are client and bucket allowlist checks; they are NOT cryptographic/encoded image byte sniffing.
   - Path Contract: Stable relative Storage object paths strictly shaped as `<auth.uid()>/<productId>/<generated-filename>.<ext>` (3 segments). Validated client-side: public/signed URLs, file://, data URIs, bucket prefixes, and invalid segment counts are rejected.
   - Upsert: Strictly upsert = false (matches Migration 010/011 where no UPDATE policy exists).
   - Return Value: Returns stable relative Storage object path (NOT signed URL, NOT local path).

6. Private Image Viewing & Signed URLs:
   - Storage service provides createSignedImageUrl(storagePath, expiresInSeconds).
   - Short-lived signed URLs are generated on-demand for private viewing; they are NEVER persisted in public.products or ProducerProduct.images.

7. No DB / Storage Atomic Transaction & Compensating Actions:
   - Supabase Storage and PostgreSQL are distinct backend services without distributed 2PC transactions.
   - If Storage upload succeeds but subsequent database image update fails, client/service architecture is designed to trigger compensating Storage deletion.

8. Product Delete Lifecycle Order: Storage First -> DB Second:
   - Storage DELETE policy verifies product ownership through private.producer_owns_product against public.products.
   - If database row is deleted first, ownership evidence is lost and Storage images become permanently undeletable orphaned files.
   - Fail-Safe Cases:
     * CASE A (no images): Deletes owned DB row normally.
     * CASE B (images present + image service available): Deletes all referenced Storage images first. Only if ALL succeed is the DB row deleted.
     * CASE C (images present + NO image service): DO NOT delete DB row. Throws typed ProductOperationException to preserve DB row and image references for retry.
   - Partial Storage Delete Failure:
     If deleting image A succeeds and B fails, DB row is NOT deleted. DB + Storage deletion is not atomic, but preserving the DB row retains ownership evidence for remaining files and allows retry/recovery.
   - Runtime Wiring:
     ProducerProductService default constructor wires ProducerProductImageService so My Products deletion at runtime possesses Storage cleanup capability.

9. Voice & AI Readiness:
   - Canonical field setters on AddProductProvider (setName, setCategory, setDescription, setPriceFromPaise, setPriceFromRupeesText, setUnit, addImagePath) serve as the unified write path for future keyboard forms, voice extraction, and AI Studio suggestions.

REAL PRODUCT PHOTO SELECTION & SECURE UPLOAD ARCHITECTURE (STEP 6C.6A)
------------------------------------------------------------
1. Picker Architecture & Injectable Abstraction:
   - File: lib/producer_section/products/services/producer_image_picker_service.dart
   - Contract: IProducerImagePickerService with production implementation ProducerImagePickerService wrapping image_picker (^1.2.3).
   - Enables 100% offline, deterministic widget and provider testing via FakeImagePickerService without requiring device cameras or galleries.
   - Picker parameters: maxWidth: 1280, maxHeight: 1280, imageQuality: 80.
   - UI choices: Clear modal bottom sheet offering Camera ("Take Photo") and Gallery ("Choose from Gallery") with large touch-friendly targets (>= 48dp).

2. Private Storage Flow & Stable Path vs Signed URL:
   - Bucket: Dedicated private 'product-images' bucket (established in Migration 010 and 011).
   - Stable Storage Path: Relative 3-segment path `<auth_uid>/<product_id>/<random_hex_32>.<ext>`.
   - Domain Model Rule: `ProducerProductDraft.images` and database column `products.images` store ONLY stable relative Storage object paths.
   - Invariant: Local filesystem paths, XFile paths, file:// URLs, raw bytes, base64 strings, and signed URLs NEVER enter `draft.images` or `products.images`.
   - In-Memory Preview & Signed URLs: For display, the provider creates short-lived signed URLs on-demand via `ProducerProductImageService.createSignedImageUrl()`. These signed URLs remain transient in-memory state and are never persisted to the database. Broken or expired signed URLs fail gracefully without crashing the UI.

3. Format & Size Validation:
   - Allowed declared MIME types: `image/jpeg`, `image/png`, `image/webp`.
   - Unsupported format rejection: Files with unsupported MIME types or extensions (e.g., HEIC/HEIF, GIF, BMP, TIFF) are rejected upfront with a localized user-friendly message asking the user to choose another photo.
   - Verification honesty: Declared MIME and extension checks are verified through `ProducerProductImageService.normalizeMimeType()`; there is no byte-level cryptographic/content sniffing yet.
   - Size limit: 5 MB maximum (matching backend Storage bucket limit). Client checks size before attempting upload and rejects oversized photos with localized feedback.
   - No guaranteed compression claims: imageQuality does not guarantee exact 300-600 KB output; size is validated truthfully.

4. Prerequisite: Persisted Product ID:
   - Storage RLS policy enforces `private.producer_owns_product(product_id)`.
   - An upload cannot proceed without a valid persisted `productId`.
   - The UI automatically ensures draft persistence before entering Step 3. Defensively, if `persistedProductId` is missing, upload fails safely without generating arbitrary/random product IDs.

5. Upload & Compensating Cleanup Lifecycle:
   - Flow: Pick image -> validate size and MIME -> read bytes -> upload to Storage via `ProducerProductImageService` -> receive stable Storage path -> update `products.images` via `ProducerProductService.updateProductImages` -> update in-memory draft and refresh signed URLs.
   - Cross-service non-atomicity: Supabase Storage and PostgreSQL are separate services and do not participate in atomic 2-phase commit transactions.
   - Failure cleanup: If the database update fails AFTER a successful Storage upload, a best-effort compensating delete is triggered immediately for ONLY the newly uploaded Storage object. Previously persisted product photos remain completely untouched.
   - Concurrency protection: `isUploadingImage` flag guards against duplicate taps and concurrent uploads.

6. Photo Removal Lifecycle:
   - Recommended order: Database-first -> Storage-delete-second.
   - Removal flow:
     (1) Compute new image path list without the removed path.
     (2) Persist updated list to `products.images` via `ProducerProductService.updateProductImages`.
     (3) Only AFTER the database update succeeds, delete the object from Storage via `ProducerProductImageService.deleteProductImage`.
   - Invariant: If database update fails, Storage object is NOT deleted, preserving referential consistency. If Storage deletion fails after DB update, the product row remains correct; orphan cleanup can occur asynchronously.
   - The product row itself is never deleted during photo removal.

7. Client-Side Maximum 4 Photos Rule:
   - Maximum photos allowed in the creation UI is 4.
   - When 4 photos exist, the "Add Photo" button is disabled/hidden and a localized badge ("Maximum 4 photos reached") is shown.
   - This is documented as a client-side product creation rule, not an immutable database constraint.

8. Product Activation & Buyer Visibility Boundaries:
   - Photos are NOT required to mark a product active under Migration 009. A product can be marked active once name, category, and positive price are provided.
   - Security & Visibility: Under Migration 009, public.products RLS restricts SELECT, INSERT, UPDATE, and DELETE strictly to the product owner (`auth.uid() = producer_id`). Active products are NOT yet readable by Buyer accounts. No Buyer marketplace visibility is claimed.


AI "IMPROVE PHOTO" ARCHITECTURE & MARKETPLACE-READY ENHANCEMENT (STEP 6C.6B)
------------------------------------------------------------
1. Purpose & Flow:
   - Provides every uploaded product photo with an optional "✨ Improve Photo" action.
   - Clean marketplace-ready transformation: removes distracting backgrounds, places product on clean neutral/light background, improves lighting and centering naturally.
   - Strict User Choice: Never automatically overwrites or replaces original image. Shows a side-by-side comparison ("Original" vs "Improved") with explicit choices: [Keep Original] or [Use Improved Photo].

2. Server-Side Edge Function Architecture & Secret Isolation:
   - Function Path: `supabase/functions/improve-product-photo/index.ts`
   - Invocation: Flutter client calls only the authenticated Supabase Edge Function via `supabaseClient.functions.invoke('improve-product-photo', ...)`.
   - Secret Isolation: AI vendor API keys (e.g. `OPENAI_API_KEY`) and service-role credentials reside strictly on the server in Deno environment variables. Zero AI API keys exist in Flutter Dart code, pubspec, app bundles, git, or client-side storage.

3. Strict Source Ownership & RLS Verification:
   - Client sends `productId` and `sourceStoragePath`.
   - Edge Function independently verifies:
     (1) Request has a valid authenticated JWT (`auth.uid()`).
     (2) Product exists in `public.products` and `product.producer_id == auth.uid()`.
     (3) `sourceStoragePath` has valid 3-segment shape `<user_id>/<product_id>/<filename>`.
     (4) `segments[0] == auth.uid()` and `segments[1] == productId`.
     (5) `sourceStoragePath` exists in `product.images` array.
   - Any ownership or shape mismatch is rejected immediately with 401, 403, or 404.

4. Strict Product-Preservation Prompt:
   - Fixed, server-owned edit instruction (zero raw client prompt injection):
     "Create a clean marketplace-ready product photo from this exact source image.
      Preserve the product exactly as shown: same shape, proportions, colors, materials,
      patterns, embroidery, printed text, logos, packaging details, quantity, and design.
      Do not add or remove product features.
      Only improve presentation:
      remove distracting background, use a clean neutral/light background,
      center the product, improve lighting and clarity naturally,
      and keep realistic shadows where useful.
      Do not stylize or redesign the product."
   - AI is forbidden from redesigning the product, adding props/labels, changing colors, or inventing packaging.

5. Storage Invariants & Original Retention:
   - Improved candidate is saved as a NEW immutable object in private `product-images` bucket:
     `<auth_uid>/<product_id>/<random_hex_32>.png`.
   - `upsert: false` is strictly enforced; original file is never overwritten.
   - Original file remains intact in Storage even after "Use Improved Photo" for recoverability.
   - Output format: PNG/JPEG, 1024x1024, compatible with Migration 010 private bucket rules.

6. Candidate State & Database Lifecycle:
   - Edge function returns `{ success: true, improvedStoragePath, sourceStoragePath }`.
   - Edge function does NOT mutate `public.products.images`.
   - Transient Provider State: Candidate path stored in `_improvedCandidates[originalPath]`. Signed URLs for candidate preview remain in-memory only.
   - Decision A: User taps "Use Improved Photo":
     (1) Replaces original path with candidate path in image list.
     (2) Updates database `products.images` FIRST via `ProducerProductService.updateDraft`.
     (3) Only after DB update succeeds, updates canonical `_draft.images`.
     (4) If DB update fails, original image remains canonical in draft and DB.
   - Decision B: User taps "Keep Original":
     (1) Canonical draft and DB remain completely unchanged.
     (2) Candidate removed from state.
     (3) Triggers best-effort deletion of unused candidate object from Storage (`discardCandidateImage`).
   - Cross-Service Non-Atomicity: Storage and Postgres operations are non-atomic; DB update always precedes state swap, and failure leaves original intact.

7. Testability & Dependency Injection:
   - Abstract contract: `IProductPhotoEnhancementService`.
   - Production implementation: `ProducerProductEnhancementService`.
   - Testing fake: `FakeProductPhotoEnhancementService` enables 100% offline, deterministic Flutter unit and widget testing without calling live OpenAI APIs.
   - Backend logic tested via `test/edge_function_test.mjs` verifying authentication, authorization, size/MIME validation, output formatting, and secret protection.

8. Limitations & Status:
   - Live AI processing requires `OPENAI_API_KEY` configured in Supabase Edge Function environment.
   - Prototype rate limiting: Per-request concurrency guards and busy state in client; edge function verifies ownership and single-image processing per call.
   - Active products remain Producer-owner-only under Migration 009; no Buyer marketplace visibility is claimed.

   - Domain Initialization: `AddProductProvider.forExistingProduct` initializes with `persistedProductId = existingProduct.id`, populates draft fields (name, category, description, price, unit, images), and sets `isEditMode = true`.
   - Anti-Duplication: Save operations call `ProducerProductService.updateDraft(productId: persistedProductId, ...)` instead of `createDraft`, guaranteeing the exact same database row is updated.
   - Active Product Preservation: Editing an active product updates content attributes while preserving `ProductStatus.active` (does not reset to draft).
   - Image & AI Preservation: Existing photos load via transient signed URLs, photo add/remove continues to function, and AI Photo Improvement workflows remain fully accessible.
   - Instant Refresh: On successful edit, the sheet returns `true` and `ProducerProductsTab` immediately updates the local provider collection.

5. Status Transition Rules:
   - Active -> Inactive (`active` -> `hidden`): Immediately updates via `ProducerProductService.updateProductStatus`.
   - Inactive -> Active (`hidden` -> `active`): Readiness validation enforced prior to activation:
     * `name.trim().length >= 2`
     * `category.trim().length >= 2`
     * `pricePaise != null && pricePaise > 0`
   - Incomplete products are blocked from activation with a localized guidance message directing the producer to edit the product first.

6. Delete Lifecycle & Fail-Safe Cleanup Ordering:
   - Storage Deletion First: When deleting a product, all associated Storage objects in `product.images` MUST be deleted BEFORE deleting the database row.
   - RLS Dependency: Migration 011 policies authorize Storage deletion based on existing ownership in `public.products`. Deleting the DB row first would orphan storage files and violate RLS on subsequent delete attempts.
   - Confirmation Dialog: Clear, destructive confirmation dialog ("Delete product? / This will permanently remove this product and its photos.").
   - UI Update: On successful deletion, product is removed immediately from provider in-memory state. On failure, the card remains intact and a localized error is shown.

7. AI Original/Candidate Storage Limitation Note:
   - When a user chooses "Use Improved Photo", the canonical `products.images` points to the improved image path while the original file remains in Storage for recoverability.
   - Product deletion cleans all paths present in `product.images`.
   - Non-canonical original sources from AI improvement that are no longer listed in `product.images` are not automatically tracked or deleted by product delete, representing an acceptable prototype storage orphan limitation.

8. Privacy & Security Invariants:
   - Storage bucket `product-images` remains 100% private.
   - Signed URLs are transient in-memory previews only (never stored in DB).
   - No service-role key is ever exposed in client code.

9. AI Product Photo Improvement Architecture (Hugging Face Inference Providers):
   - End-to-End Pipeline:
     Flutter ProducerProductDetailsView -> improve-product-photo Supabase Edge Function ->
     Bearer JWT verification + product ownership/path validation -> private Storage download ->
     in-memory minimum dimension validation (upscaled via @jsquash WASM if <256x256 while preserving aspect ratio) ->
     Hugging Face Inference Providers (`@huggingface/inference`) with provider="auto" ->
     Model: `Qwen/Qwen-Image-Edit` -> magic byte detection (PNG/JPEG/WebP) ->
     uploaded to private `product-images` as `<userId>/<productId>/<hex_id>.<ext>` (upsert: false) ->
     transient signed URL pre-warming -> interactive Before/After comparison modal ->
     explicit producer selection ("Keep Original" discards candidate / "Use Improved Photo" persists to products.images).
   - Security Invariants:
     * `HF_TOKEN` is read strictly server-side via Supabase Edge Function environment secrets.
     * Zero API keys or service role secrets present in Flutter client code, Dart, or git.
     * Sanitized error messages presented to users on failure; technical diagnostics confined to server logs.
     * Original producer photo in Supabase Storage is never mutated or overwritten during AI enhancement.
   - Live Verification Result:
     * Manually tested and confirmed functional in the live mobile application.
