DATABASE FOUNDATION ARCHITECTURE (STEP 6B.1)
------------------------------------------------------------
1. Canonical Schema:
   - Table: public.products
   - Primary Key: id UUID DEFAULT gen_random_uuid()
   - Ownership FK: producer_id UUID NOT NULL REFERENCES public.producer_profiles(id) ON DELETE CASCADE
   - Identity Relationship: producer_profiles.id == profiles.id == auth.users.id. Only verified/registered producers can own products.
   - Core Fields: name, description, category, price, unit, images, status, created_at, updated_at.

2. Product Lifecycle States:
   - Exactly 3 states: 'draft', 'active', 'hidden'.
   - 'draft': Work-in-progress, unlisted, visible only to owner.
   - 'active': Completed product, ready for future discovery, visible only to owner in Step 6B.
   - 'hidden': Temporarily delisted by producer (e.g. out of stock), visible only to owner.
   - No premature moderation workflows ('under_review', 'needs_changes', 'rejected') fabricated.

3. Pricing & Currency Rule:
   - Type: NUMERIC(12, 2) in INR (accommodates up to ₹9,999,999,999.99 with exact paise precision).
   - Drafts: Price may be NULL while incomplete.
   - Positive Price: If price is provided, it must be > 0.
   - Active Requirement: An 'active' product MUST have a valid positive price (> 0).

4. Text & Unicode Preservation:
   - Fields: name, description, category, unit.
   - Rule: Original user-entered Unicode text (English, Hindi, Punjabi, etc.) is preserved as-is.
   - Zero destructive overwriting with AI-generated or translated text.

5. Image Reference Strategy:
   - Field: images TEXT[] NOT NULL DEFAULT '{}'.
   - Storage-relative paths or references. Zero fake remote URLs.
   - Storage Bucket: Dedicated 'product-images' bucket and secure upload policies explicitly deferred to Step 6C.

6. Security & Row Level Security (RLS):
   - RLS strictly enabled on public.products.
   - SELECT, INSERT, UPDATE, DELETE strictly scoped to auth.uid() = producer_id.
   - Active products remain owner-only in Step 6B. Public/Buyer discovery deferred.
   - Hard Delete adopted for prototype simplicity.

7. AI & Voice Data Boundary:
   - Base table stores strictly canonical product attributes.
   - Zero speculative AI prompts, embeddings, audio blobs, or marketing metrics in the schema.
   - Future AI Studio and voice guidance will map directly to these canonical columns.


DART DOMAIN, SERVICE & PROVIDER FOUNDATION (STEP 6B.2)
------------------------------------------------------------
1. ProducerProduct Domain Model:
   - File: lib/producer_section/products/models/producer_product.dart
   - Immutable data model with const constructor and copyWith support.
   - Exact mapping to PostgreSQL public.products schema columns.
   - Monetary Representation (Step 6B.2A): PostgreSQL stores NUMERIC(12, 2); Dart domain stores exact integer paise (`int? pricePaise`, where ₹1 = 100 paise), avoiding floating-point precision hazards.
   - Service/model boundary converts deterministically: string/num to paise on read, and paise to two-decimal string on write.
   - Currency formatting remains strictly a presentation/localization concern.
   - Images represented as List<String> storing storage references.
   - Original Unicode strings preserved without modification.

2. ProductStatus Enum Mapping:
   - Values: draft <-> 'draft', active <-> 'active', hidden <-> 'hidden'.
   - Controlled FormatException thrown on unknown or malformed database status.
   - Zero silent fallback to draft to protect data integrity.

3. ProducerProductService:
   - File: lib/producer_section/products/services/producer_product_service.dart
   - Responsibilities: fetchProducts (ordered by created_at DESC), updateProductStatus, and hard deleteProduct.
   - Authenticated Ownership: Scoped strictly to auth.uid() = producer_id.
   - Exception model: ProductAuthException (when unauthenticated) and ProductOperationException (sanitized errors).

4. ProducerProductsProvider:
   - File: lib/producer_section/products/providers/producer_products_provider.dart
   - Responsibilities: Owns full product list, visible filtered list, loading lifecycle, and error state.
   - Filter Strategy: Local in-memory filtering across All, Active, Draft, and Hidden. Avoids redundant server round-trips upon tab switching.
   - Loading & Error States: Truthfully distinguishes initial, loading, loaded empty, and loaded with items. Safe categorized error enum (none, notAuthenticated, loadFailed, updateFailed, deleteFailed) prevents raw Postgres strings in UI.
   - Zero UI Coupling: Presentation-independent (no BuildContext, widgets, or localization dependencies).

5. Offline-Test Dependency Injection:
   - Abstract contract IProducerProductService allows injecting mock/fake services.
   - 100% offline, deterministic testing with zero live Supabase requirement.

6. Boundaries:
   - Storage Boundary: Still deferred to Step 6C (images are raw string references only).
   - Buyer Boundary: 100% isolated. Zero imports from buyer_section or Buyer mock data.
