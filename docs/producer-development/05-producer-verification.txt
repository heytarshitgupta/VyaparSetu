2. TRUST BOUNDARIES & DATA MINIMIZATION
------------------------------------------------------------
- Raw Aadhaar Prohibited: Zero 12-digit Aadhaar numbers are accepted or stored.
- Trusted Identity Artifacts (Backend-Only):
  * aadhaar_last4 and aadhaar_verification_reference (token/reference returned by future verification service)
  * pan_last4 and pan_hash (backend-generated protected fingerprint or reference token; plaintext PAN is NEVER stored)
  * These columns are NOT client-writable and cannot be supplied directly by the Flutter app.
- GST Compliance Declaration:
  * gst_registered: Producer-supplied boolean indicating whether they are registered for GST.
  * gstin: Producer-supplied 15-character GSTIN.
  * gst_registered = FALSE means solely that the Producer declared they are not GST registered (legal threshold validation is outside prototype scope).
  * gst_verification_status defaults to 'not_applicable' when gst_registered = FALSE.
- Protected Verification Outcomes & Onboarding Status:
  * pan_verification_status, aadhaar_verification_status, gst_verification_status, address_verification_status, verification_status, and onboarding_status are strictly omitted from client write grants and can only be updated by trusted backend/admin logic.

4. STEP 4E2 — SECURE SIMULATED PAN VERIFICATION WORKFLOW
------------------------------------------------------------
A. Architecture & Boundary Distinction:
- REAL (Production Architecture Guaranteed):
  * Authenticated Supabase request: Caller identity is derived exclusively via auth.uid() inside a SECURITY DEFINER function.
  * Backend authorization: RPC asserts caller has 'producer' role in public.profiles and exists in public.producer_profiles.
  * Trust boundaries: Direct client write privileges on pan_last4, pan_hash, and pan_verification_status remain completely revoked.
  * Zero Raw PAN persistence: Plaintext 10-character PAN is NEVER stored in any database column, provider state, file, or log.
  * Trusted status updates: Successful or rejected outcomes are strictly computed and updated within the backend RPC.
  * Safe masking: Only masked identifier (e.g. '******234F') is returned to the client and presented in the UI.

- SIMULATED (Prototype Environment Scope):
  * Existence in government records: In this hackathon prototype, verification is simulated using deterministic demo evaluation rules rather than querying live Income Tax Department / NSDL / Protean registries.
  * Person match: Name/DOB matching is syntactically checked against format rules, not cross-referenced with a government database.
  * Extensibility: A live authorized PAN provider / GSTN sandbox API can seamlessly replace the internal simulation logic within verify_producer_pan_prototype without modifying client UI or data models.

B. Deterministic Demo Simulator Rule:
- Valid Input Criteria:
  * PAN normalized: UPPER(TRIM(p_pan)) matching ^[A-Z]{5}[0-9]{4}[A-Z]$
  * Name length: 2–120 characters
  * Date of Birth: Historical date (1900-01-01 <= p_dob <= CURRENT_DATE)
- Demo Evaluation Outcome:
  * Rejection Condition: PAN starting with 'FAIL' (e.g. FAILA1234B) OR having 4th character 'X' (e.g. ABCXE1234F) simulates a rejected verification (pan_verification_status = 'rejected', message = 'PAN details could not be verified with records in demo registry.').
  * Success Condition: All other valid PANs simulate successful verification (pan_verification_status = 'verified', computes pan_last4 = RIGHT(pan, 4), computes pan_hash = SHA-256 hex digest, returns masked_pan = '******' || pan_last4).

C. Flutter Integration (ProducerVerificationService):
- Dedicated service encapsulates Supabase RPC invocations.
- Sanitizes all exceptions: Network or database failures return user-friendly errors ("Unable to complete verification at this time. Please try again.") without exposing internal PostgreSQL errors.
- UI state progression: Not Verified -> Checking... -> Verified (or Could Not Verify).
- Loading state: Disables duplicate Verify taps with loading spinner.
- Success state: Replaces input form with green verified card showing only masked identifier ('******234F') and allows "Edit Details" if desired. Raw PAN is cleared from controller.
