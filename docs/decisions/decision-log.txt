- Buyer Module Isolation: The Buyer module under lib/buyer_section/ is owned by another teammate and is strictly treated as READ-ONLY for Producer development to prevent regressions.
- Standardized Terminology: The term Producer is adopted across code, routes, database schemas, and documentation (replacing "Seller" for all new development).
- Branch Strategy: Producer development occurs on the dedicated producer-development branch.
- Security-First Development: Security, authorization, and Row Level Security (RLS) are development-time requirements built incrementally at each stage, not added as a post-development polish item.
- Responsive UI Constraint: All future screens must avoid fixed-size overflows and support diverse screen sizes and text scaling via flexible Flutter layouts.
- Low-Literacy Friendly UX: UX is engineered specifically for grassroots micro-producers with clear icons, large touch targets, simplified terminology, and step-by-step guidance.
- Decoupled Language Preferences: The application architecture decouples App UI Language from Voice Guidance Spoken Language (e.g. English UI with Punjabi audio narration).
- Optional Voice Guidance: Audio guidance is strictly optional, user-controlled, and can be disabled at any time.
- Auditable SQL History: All SQL queries, migrations, and table definitions executed against Supabase must be stored as versioned files in supabase/sql/ inside the Git repository.
- Live Documentation: Documentation will use .txt files for easy reading and management. Executable database scripts will continue to use .sql.
- Preserve Nested Repo Structure: The existing nested /VyaparSetu/VyaparSetu folder structure is preserved to avoid disturbing working directory paths and tooling.
- Single Configuration Method: Project configuration is standardized on a single root .env file loaded via flutter_dotenv, with generic placeholders in .env.example.
- Database Foundation Schema & Privileges:
  * Migration 001_database_foundation.sql executed in Supabase.
  * Private-by-Default RLS enabled on profiles, producer_profiles, and app_sessions.
  * Explicit column-level privilege whitelist: direct modifications to profiles.role and producer_profiles.verification_status are disbarred for authenticated clients.
  * Concurrency enforcement: Partial unique index on app_sessions(user_id) WHERE (is_active = TRUE).
  * Secure Session RPC: register_app_session() derives user identity strictly from auth.uid(), sets search_path = '', validates 64-hex token hash, and deactivates prior sessions atomically.

- Resumable Producer Onboarding Architecture (Step 4E2.1):
  * Problem: Reopening the app, refreshing the browser, losing network connectivity, or signing out previously reset the producer to Step 1, ignoring earlier persisted draft records.
  * Server-Authoritative Progress: Stored public.producer_profiles.onboarding_step (SMALLINT, CHECK 1 to 5) as the single source of truth. Local persistence mechanisms (SharedPreferences, localStorage, static state) are rejected as authoritative sources to ensure cross-device consistency and prevent client-side bypass.
  * Progression & Anti-Skipping: Direct client UPDATE on onboarding_step is omitted. Progression is governed strictly by public.advance_producer_onboarding_step(expected_current_step, next_step) RPC (SECURITY DEFINER, search_path = '', caller auth.uid() check, producer role check). Progression allows advancement of at most 1 step beyond server's known progress.
  * Monotonic & Idempotent: If the user presses "Back" in the UI to review or re-edit prior steps, the server's persisted onboarding_step does NOT regress. The RPC treats calls where server_step >= next_step as idempotent no-ops.
  * Save-First Advancement: The server progress is updated only after the corresponding form payload save completes successfully. If save fails, progress does not advance.
  * Initial Load Restoration: On screen load, ProducerOnboardingScreen fetches producer_profiles, extracts onboarding_step, and initializes directly to the saved step with draft data prefilled.
- Security and Correctness Hardening of Migrations 006 and 007 (Step 4E2.3):
  * Migration 006 Verified Identity Protection: If caller already has pan_verification_status = 'verified', a matching PAN returns 'already_verified' (idempotent success); a differing or failing PAN returns 'already_verified_conflict' and NEVER destroys, erases, or alters verified artifacts (pan_last4, pan_hash, status).
  * Fingerprint Documentation: Clarified that sha256(pan || ':' || uid) is a prototype pseudonymous integrity fingerprint, not encryption, and production requires server-secret HMAC or vault tokenization.
  * Migration 007 Expected Step & Stale State Guard: Uses expected_current_step to enforce server_step = expected_current_step and next_step = expected_current_step + 1, guarding against stale client state and race conditions.
  * Server-Side Prerequisite Enforcement: RPC verifies saved database records (1->2 requires profiles.full_name; 2->3 requires producer_profiles business_name & craft_category; 3->4 requires valid location fields and pincode). Flutter validation is UX; RPC is the security boundary.
  * Step 4 -> 5 Blocked: Generic progression RPC rejects advancing past Step 4 ('identity_compliance_incomplete') because compliance completion rules (PAN, Aadhaar, GST, Address) are still evolving.
  * Backfill Rule Correction: Removed premature pan_verification_status = 'verified' -> 5 inference. Step 4 encompasses full identity and compliance. Added city and string length checks to Location backfill.
  * Concurrency Row Lock: Used SELECT ... FOR UPDATE on producer_profiles to serialize concurrent requests.
